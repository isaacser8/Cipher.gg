Introduction

Cipher.gg is a real-time web platform for playing hidden-role social deduction games inspired by The Resistance: Avalon. It replaces the human moderator with an automated backend game engine that handles role assignment, hidden information, voting, quest resolution, reconnection, and endgame records.

The deployed prototype is available at: https://cipher-gg.vercel.app/ 

At a high level, Cipher.gg uses React on Vercel, Node.js/Express and Socket.IO on Railway, Clerk for authentication, and MongoDB for persistence.

Beginner Overview: How the Game Works

Cipher.gg is based on a hidden-role team game. Players are secretly assigned to either the Good team or the Evil team. Good players try to complete three successful quests. Evil players try to secretly sabotage three quests or identify Merlin at the end of the game.

Each round, one player becomes the leader and proposes a team for the current quest. Everyone votes to approve or reject that proposed team. If the team is approved, selected quest members secretly submit either Success or Sabotage. If enough sabotage cards are submitted, the quest is compromised; otherwise, it is secured.

Good wins by securing three quests, but Evil gets one final chance to win by assassinating Merlin. Evil also wins if three quests are compromised or if the group rejects five proposed teams in a row.

Motivation

As busy university students but also board game enthusiasts, we find coordinating in-person social deduction games like Avalon difficult due to location constraints, manual role tracking, and the need for an experienced moderator. To solve this, we want to build a real-time coordination engine that is able to digitize the moderator role, manage hidden information, and coordinate the game flow automatically, which is how Cipher.gg came to life. We also realised that traditional physical setups suffer from a steep learning curve and require a huge amount of time to facilitate understanding for beginners, and online platforms are not all well equipped with appropriate tools for deduction (such as notes, log history, match history etc.). Thus, we also hope to make such games less intimidating by providing a beginner guide with the addition of automated system logs to ensure that amateurs and veterans all can enjoy social deduction games anytime, anywhere.

Our Aim

Our project delivers a comprehensive and interactive solution by architecting a real-time state orchestration engine tailored for hidden-identity social deduction games. Unlike generic multiplayer apps, our system acts as a secure, automated moderator that manages information asymmetry and precise data masking across a distributed player base. Using a well-known board game: The Resistance: Avalon as our core model, we aim to demonstrate flawless real-time synchronization and prove that complex tabletop mechanics can also be seamlessly and securely digitized into a highly accessible, user-friendly experience for our users.

Key Engineering Challenges

Although Cipher.gg appears as a game interface, the core engineering challenge is not rendering screens. The difficult part is maintaining a secure real-time multiplayer state machine for a hidden-role game where players are not supposed to receive the same information.

We identified five main engineering challenges:

1. Authoritative game-state orchestration: all gameplay transitions must be enforced by the backend FSM rather than trusted to the frontend.

2. Role-specific privacy: different players must receive different views of the same match state without leaking hidden roles.

3. Real-time synchronization: votes, quest actions, timers, chat, and game updates must remain consistent across multiple Socket.IO clients.

4. Failure handling: reconnecting sockets must preserve a player's seat and role without duplicating players or corrupting the game.

5. Persistent records: completed and abandoned matches must be saved accurately so profile statistics and match history remain trustworthy.

The rest of this README explains how our design addresses these challenges through modular backend managers, per-socket state masking, integration tests, and CI/CD enforcement.

System Architecture

 

Architecture Diagram

  • Frontend (Vercel): React app for the UI; Clerk Auth handles sign-in and issues tokens; Socket.IO Client keeps a persistent WebSocket connection for real-time updates.
  • Backend (Railway): Express API verifies Clerk tokens and serves HTTP requests; Socket.IO Server manages live connections and forwards player actions to the Game Engine.
  • Game Engine: A Finite State Machine enforces all game rules and state transitions.
  • Data Masking: Filters the FSM's global state into a player-specific view before broadcasting, so each client only sees what it's permitted to.
  • Database: MongoDB (via Mongoose) stores persistent records including accounts, match history.

Feature 1: Lobby & Session Management System (Final)

Hosting/Join Page

Joined Lobby

Joined Lobby As Host

As a game host or player, I can enter my display name and generate or input a unique room code. This allows me to securely join a private digital room with my specific group of friends before the game starts.

This feature is built on a client-server architecture and utilizes a session-based WebSocket protocol to manage real-time player grouping. To implement this, the Node.js backend acts as the authoritative server and uses its native crypto module to generate secure, unique room codes; while the React frontend functions as the presentation layer to handle login routing. When users authenticate locally with a display name and room code, the server validates this input and assigns their active WebSocket connection to a dedicated Socket.IO room or session pool. By partitioning the connections on the backend, the server ensures that sensitive game data and chat messages are only broadcasted to the specific players within that lobby to make data isolation possible.

There is also a validation layer that rejects display names that are blank, over 15 characters, or already active in the same room, and the lobby enforces a dynamic capacity limit configured by the host rather than a fixed cap. If a player's old connection goes stale (e.g. a duplicate tab), the server detects and disconnects it so the new session takes over cleanly, and host status transfers automatically if the original host disconnects. Every player must explicitly flag themselves as ready, and the host's "Start Game" control stays disabled until the room is full and everyone has done so.

Trade-Offs: This architectural design directly fulfills our core user story of generating private digital rooms as it guarantees that friends can connect seamlessly without cross-lobby interference or data leaks. However, it carries the same trade-off we flagged in MS1, which is that the lobby state lives entirely in server memory (RAM) rather than a persistent store, so a server restart wipes all active lobbies. The Reconnection System delivered in this milestone (see Feature 6) addresses the player-facing half of this problem — an individual dropping and rejoining — but the underlying constraint remains: state lives in the server process, so a restart still wipes active lobbies. Moving this state into an external store such as Redis remains the natural next step (see Known Limitations). We also weighed auto-starting the match the moment the room filled, but we chose the explicit Ready Up step instead, since auto-start risked starting the game for a player whose client hadn't fully caught up. That's a bug we'd rather design out at the protocol level than patch reactively later.

Sub-Feature 1.1: Authentication

User Authentication Page

Players can sign in with social providers or email through Clerk, or skip sign-in entirely and join as a guest with just a display name whichever is faster for the group.

The system delegates identity management to Clerk for session handling instead of rolling a custom authentication backend which frequently introduces security vulnerabilities as the React frontend interfaces directly with Clerk's SDK. Upon successful authentication, Clerk issues a cryptographically signed, short-lived JWT and the frontend passes this token to the Node.js backend during the initial WebSocket handshake, allowing the server to verify the client's identity statelessly before authorizing access to the orchestration engine. For guest play, no Clerk ID is required, and the server simply registers the player by their display name without creating a persistent user record.

Trade-Offs: Supporting both signed-in and guest paths means match history is inconsistent across them — a guest's result is saved to the match record but isn't linked to any persistent profile, so unlike a signed-in player, they can't look back on a personal win rate and match history later. We accepted this because forcing sign-in would reintroduce exactly the friction we built guest play to avoid: for casual game nights, asking everyone to authenticate before they can even join a room is a real barrier. Players who care about long-term stats can opt into Clerk; players who just want to play tonight don't have to.

Feature 2: Automated Game Master (Final)

(Detailed visuals are presented below in sections for Sub-Features)

As a player, the platform automatically transitions me and my friends through every phase of an Avalon match, from role assignment through team voting, quest execution and the final assassination without anyone needing to track turns or moderate the game manually.

This feature is built upon a finite state machine (FSM) operating under a strict zero-trust server model. The core game logic is completely decoupled from the frontend and isolated on the Node.js backend, where the FSM owns every phase transition. A match begins in LOBBY, moves through ROLE_ACKNOWLEDGEMENT and PRE_GAME_STRATEGY, then enters the core quest cycle: TEAM_SELECTION → TEAM_VOTING, branching to either QUEST_EXECUTION (if the team is approved) or VOTE_FAILED (if rejected, which loops back to TEAM_SELECTION under the next leader). After QUEST_RESULT, the cycle repeats until three quests succeed or fail, at which point the engine moves to ASSASSINATION_PHASE (if Good would have won) and finally GAME_OVER.

Each transition is guarded by an assertion on the current state, so any action sent out of turn, like a non-leader trying to propose a team, a player trying to vote twice, an event arriving for a phase that has already ended is rejected with an explicit error before it can corrupt the game state. We use the term finite state machine here deliberately rather than Saga Pattern, as the FSM runs in a single process and guards transitions, whereas a Saga coordinates distributed transactions across services with compensating rollback actions. The vote-rejection loop in particular may resemble a Saga at first glance, but it is a state transition rather than a rollback — failed votes are recorded permanently in the match history, not reversed, so no compensating actions are needed.

On top of the phase machinery, the engine enforces the full Avalon ruleset: the RoleAssigner module uses cryptographic shuffling to randomly distribute roles and the correct good/evil ratio for any lobby size between 5 and 10 players; the QuestManager rotates leadership clockwise after each team rejection and tracks the 5-consecutive-rejection loss condition (Evil wins automatically if no team is ever approved); and the AssassinationManager handles the endgame branch where Evil can still steal the win by correctly identifying Merlin. Per-quest team sizes and the "two-fail required" rule for Quest 4 in larger lobbies are also handled dynamically based on player count, matching the official Avalon rulebook.

The frontend never sees the full game state. Instead, a server-side presenter (gameStatePresenter.js) filters the FSM's output per-socket before broadcasting, so each player only receives the intel their role is entitled to: Merlin sees both Evil identities, Evil sees their teammates, and Loyal Servants see nothing. The React UI is reduced to rendering whatever the server hands it and emitting player actions with no game logic of its own.

Backend Game Engine Module Design

The backend game engine is split into focused modules instead of placing all game logic inside the socket handlers.

  • GameStateMachine owns the current phase and controls legal transitions.
  • RoleAssigner handles role distribution and role validation.
  • QuestManager handles team proposals, vote tallying, quest outcomes, and the five-rejection evil win condition.
  • AssassinationManager handles the final Merlin assassination branch.
  • gameStatePresenter transforms the full internal game state into player-specific payloads.

This follows the same SE principle of separation of concerns as socket handlers act as controllers where they receive events, validate room/player context, and delegate to the correct game-engine module. This makes the engine easier to test because role assignment, quest logic, and assassination logic can be unit-tested independently.

FSM Design Discussion

Finite State Machine (FSM) Diagram for Gameplay

The FSM is the core design decision behind Cipher.gg. Instead of allowing the frontend to decide which actions are valid, every incoming player action is checked against the current server-side phase. For example:

  • propose_team is valid only during TEAM_SELECTION and only from the current leader.
  • submit_vote is valid only during TEAM_VOTING.
  • submit_quest_vote is valid only during QUEST_EXECUTION and only from selected quest members.
  • submit_assassination is valid only during ASSASSINATION_PHASE and only from the Assassin.

This prevents a common real-time multiplayer bug where the server accepts an event just because it arrived. In our design, an event must pass phase validation, role/player validation, and room validation before it can mutate the game state.

The FSM diagram also makes the rejection branch explicit. If a proposed team is rejected, the game enters VOTE_FAILED, rotates leadership, and returns to TEAM_SELECTION. If five proposed teams are rejected consecutively, the game ends immediately with an Evil win. This branching logic is one reason we chose a finite state machine: it gives every legal and illegal transition a clear place in the design.

Trade-Offs: Putting the entire ruleset on an authoritative server increases backend computational load and requires every client to maintain a stable WebSocket connection throughout a match. A client-authoritative or peer-to-peer model would have lowered server costs and tolerated brief network drops more gracefully. However, it would be defenseless in a social deduction game where players are incentivized to inspect browser storage, forge network packets, vote out of turn, or force illegal state transitions. For this reason, zero-trust server authority is the only design that makes the rules enforceable, so the trade-off is worthwhile.

Sub-Feature 2.1: Role Assignment, Information Hiding

Role Reveal Modal

When the game starts, each player sees a RoleRevealModal confirming their assigned role and any intel they are entitled to. While players read and confirm their roles, the dashboard renders an "Awaiting Acknowledgements" header indicating that the FSM is in ROLE_ACKNOWLEDGEMENT and waiting for every player to click their "Acknowledge Directive" button (see Sub-Feature 4.5). Once every player has confirmed, the FSM transitions to PRE_GAME_STRATEGY for the first round of coordination (see Sub-Feature 2.2).

The intel each player receives is filtered server-side by their role. Merlin sees both Evil agents, the Assassin and Mordred's Minion see each other as Evil, and Loyal Servants receive no intel at all — they are told only their alignment, with no visibility into anyone else's role. This filtering happens entirely in gameStatePresenter.js before the role payload is broadcast, so no client ever receives information beyond what its role permits, regardless of any attempt to inspect or tamper with the response on the frontend. After the modal is acknowledged, the same intel persists in the player's RoleCardPanel for the rest of the match (see Sub-Feature 4.3), so players can refer back to their role and intel without needing to remember the initial reveal.

Awaiting Acknowledgements Page

Sequence diagram for role assignment and data masking

Zero-Trust Data Masking

A key design choice is that the frontend is never trusted with hidden information. Even though React conditionally renders panels, the security boundary is not the React UI. The actual security boundary is the backend presenter. The full internal game state may contain all player roles, teams, votes, quest results, and hidden information. Before broadcasting, gameStatePresenter.js constructs a different payload for each socket:

Player Type

Data Received

Merlin

Evil player identities, but not the full role table

Loyal Servant

Own role/team only

Assassin

Assassination target panel only during assassination phase

Evil player

Evil teammates

Quest player

Quest action panel only if selected

Non-quest player

Waiting state only during quest execution

This means a malicious client cannot reveal hidden roles by inspecting browser state, because the browser never receives data it is not supposed to see.

Sub-Feature 2.2: Pre-Game Strategy Phase

Strategy Phase

After every player clicks "Acknowledge Directive" on their Role Reveal Modal, the FSM transitions from ROLE_ACKNOWLEDGEMENT to PRE_GAME_STRATEGY, opening a 30-second window before the first quest begins. During this phase, Evil players gain access to a private Evil-only channel in the chatbox (see Feature 3) so they can identify their teammates and coordinate without exposing themselves to Good players. The engine enforces both the phase boundary and the channel gating: the Evil chat toggle is only available while the FSM is in PRE_GAME_STRATEGY, and the server rejects any message routed to the Evil channel from a Good-aligned socket regardless of what the client sends. When the timer expires, the FSM automatically advances to TEAM_SELECTION for the first quest, closing the Evil channel for the rest of the match.

Sub-Feature 2.3: Team Selection

Team Selection Phase

The current leader selects a team of size teamSize[questNumber] from the active player roster, while every other player sees a waiting state until the proposal is submitted. The engine enforces that only the current leader's submission is accepted and that the team size matches the rulebook for the current quest and player count — any other submission is rejected with an explicit error. The TeamSelectionPanel renders the selection controls only for the leader (see Sub-Feature 4.5 for the panel's UI specifics).

Sub-Feature 2.4: Team Voting

Voting Phase

Once a team is proposed, every player simultaneously votes to approve or reject it. The server collects votes through the TeamVotingPanel, tallies them, and either advances the game to QUEST_EXECUTION (majority approval) or transitions to VOTE_FAILED, which rotates the leader and loops back to TEAM_SELECTION. Vote history is recorded permanently in the match state so players can scrutinize each other's voting patterns. If five teams are rejected consecutively without a single approval, the QuestManager ends the match with Evil winning automatically — preventing an indefinite stall.

Sub-Feature 2.5: Quest Execution

Quest Execution Phase

Players selected for the quest each privately submit a Success or Sabotage card through the QuestExecutionPanel. The engine renders the Sabotage option only to Evil players and rejects any Sabotage submission from a Good-aligned socket on the server side, regardless of what the client sends. The quest passes if all submitted cards are Success and fails otherwise. Individual card submissions remain anonymous — only the aggregated pass/fail result and the count of Sabotage cards (without revealing who played them) is broadcast through gameStatePresenter.js.

Sub-Feature 2.6: Assassination

Assassination Phase

If Good would otherwise win by completing three successful quests, the FSM transitions to ASSASSINATION_PHASE rather than ending the game immediately. The AssassinationManager gives the Assassin a one-shot decision to identify Merlin from the player roster — a correct guess flips the outcome to an Evil win, while an incorrect guess confirms Good's victory. Only the Assassin's socket is permitted to submit a target, and the panel (see Sub-Feature 4.5) only renders for that player. Once the Assassin submits their target, the FSM transitions to GAME_OVER and the outcome is handed off to the Endgame Summary (see Feature 5).

Feature 3: Real-Time Text Chat (Final)

Real time text chat for players in lobby/in-game

    Exclusive evil channel for pre strategy           Search feature to secure keywords

As a player, I can communicate with everyone in my room through a real-time chatbox during both the lobby and in-game phases which helps us to debate, defend, accuse, coordinate quest decisions, and review previous messages without relying on external apps like Discord, WhatsApp, or Telegram.

In this milestone, the chatbox was also upgraded with a search feature, allowing players to quickly filter past messages and find important accusations, claims, or strategic comments during a match.

This feature is built on an event-driven WebSocket architecture using Socket.IO between the React frontend and the Node.js backend. Unlike a traditional request-response HTTP model where the frontend must repeatedly ask the server for new messages, Socket.IO maintains a persistent connection between each client and the server. When a player sends a message, the React ChatBox emits the message content and selected channel. The backend derives the sender and room from the authenticated socket context rather than trusting client-provided identity fields, validates that the socket belongs to the room, and then broadcasts the message only to the correct Socket.IO room or Evil-only channel. This ensures that conversations remain isolated between private lobbies and prevents messages from leaking across different game sessions.

The chat system is not treated as a separate side feature, but as part of the core social deduction loop. In Avalon, communication is part of the main gameplay as good players need to question suspicious behaviour, evil players need to lie convincingly, and special roles such as Merlin must guide the team without exposing themselves. By embedding chat directly into the lobby and game dashboard, we are able to keep deduction, accusations, team discussions, and strategy inside the same interface where voting and quest actions happen. This reduces context switching and makes the platform feel like a complete digital moderator rather than only a game-state tracker.

For the final version of this feature, we also implemented a chat search layer on the frontend. The ChatBox component stores the received chat history in React state and uses a search toggle to reveal an input field when needed. The displayed messages are derived from the original message list using a filter, so the underlying chat history is never mutated or overwritten by the search operation. If the search query is empty, the full message list is shown; if the query matches some messages, only those matching messages are displayed; and if no messages match, the UI shows a "No results found" state. This handles an important usability issue in longer games where players may need to retrieve earlier claims such as "I am Merlin", "failed the quest", or "pushed that team too quickly" without manually scrolling through the entire chat log.

The chatbox also supports communication for Evil players during the pre-game strategy phase. When a player is on the Evil team and the game is still in the strategy phase, the interface allows them to switch between global chat and Evil chat. This design supports Avalon's hidden-team coordination while still preserving the integrity of the public discussion space. The frontend only exposes the channel controls when the player's role/team and current phase permit it, while the server remains responsible for room-level broadcasting and message isolation. This server-side validation is important because Evil chat is not only a UI toggle; it is a hidden-information permission boundary. Even if a modified client tries to send to the Evil channel, the backend rejects the message unless the socket belongs to an Evil player and the FSM is still in PRE_GAME_STRATEGY.

Trade-Offs: Choosing WebSockets over HTTP polling increases backend resource usage because every active player maintains a persistent connection to the server. This consumes more memory and makes future horizontal scaling more complex than a fully stateless REST-based design. However, HTTP polling would introduce noticeable latency because clients would only receive new messages when they next ask the server for updates, which is unsuitable for a live social deduction game where timing, persuasion, and rapid responses matter. The search feature also currently runs entirely on the client, which is simple and fast for normal match-length chat histories, but it means very large logs could eventually become less efficient if the game expands into long-term match archives. We accepted this trade-off because in-game chat histories are small enough for client-side filtering, and keeping search local avoids unnecessary backend complexity for this milestone.

Feature 4: Dynamic Player Dashboard (Final)

Dashboard Overview

As a player, I can view a live game dashboard that updates instantly as the match progresses, showing me the current mission status, player roster, my private role information, the active phase, the phase timer, and any actions I need to take. This means I do not need to manually track whose turn it is, which quest is active, who has been selected for a team, or whether the game is waiting for my vote. The dashboard acts as my command centre throughout the match.

This feature is built using reactive frontend state synchronized with server-emitted Socket.IO events. The React frontend maintains the current game view through shared socket context and component-level state, while the Node.js backend remains the authoritative source of truth for the actual game state. Whenever a player joins, readies up, proposes a team, votes, submits a quest action, or triggers a phase transition, the backend emits updated payloads such as roster updates, game state updates, vote results, quest results, and game-over data. The frontend listens for these events and re-renders the relevant dashboard panels immediately without requiring any manual refresh. Importantly, the dashboard performs no secret game logic on the client — it renders only the filtered payload prepared per-socket by the backend (see Feature 2), preserving the zero-trust security model while keeping the interface responsive.

The dashboard is intentionally modular, composed of two categories of panels. Four always-on panels are visible throughout the match and re-render as state changes — the Agent Roster, Mission Progress, Role Card, and Private Notepad — and are documented as Sub-Features 4.1 to 4.4 below. Six phase-specific panels — the Awaiting Acknowledgements header, Strategy Phase header, Team Selection, Team Voting, Quest Execution, and Assassination — appear only during their corresponding FSM phase and disappear once the phase ends; these are covered in Sub-Feature 4.5, with their engine-side rules described in Feature 2. A countdown timer is also surfaced at the top of the dashboard during action phases like Team Selection and Voting, with the deadline set by the server's phase state.

Trade-Offs: Mapping the dashboard directly to live WebSocket updates makes the interface highly responsive, but it also means the user experience depends heavily on connection stability. If a connection silently drops, the player may temporarily see stale information until the server detects the disconnect or the client reconnects. We deliberately kept this recovery logic out of the dashboard itself and implemented it as a dedicated feature instead (see Feature 6 — Reconnection System), so the dashboard remains a pure rendering layer over whatever state the server hands it. A dropped client is now detected server-side and its state preserved through a grace period, allowing the dashboard to resync on reconnect rather than needing its own recovery logic.

This is especially important in social deduction games because players often need to track soft information over time — who pushed a suspicious team, who defended whom, who contradicted an earlier statement, or who may be hiding as Merlin. Notes are kept entirely client-side in browser storage, so they remain private even from the server.

Feature 5: Endgame Summary (Final)

Good Victory (Assassin failed to identify Merlin)          Evil Victory (5 consecutive rejected teams)

Evil Victory (Assassin correctly identified Merlin)               Evil Victory (Evil sabotaged 3 quests)

As a player, when a match ends, I can immediately see the final outcome of the game, the reason that side won, the final quest score, and the fully revealed identities of every player. This allows everyone in the room to understand exactly how the game concluded — whether Good won because the Assassin failed to identify Merlin, Evil won because Merlin was assassinated, Evil won because three quests were sabotaged, or Evil won because the lobby failed to approve any team across five consecutive votes.

This feature is built as the final output stage of the backend game engine. When the finite state machine reaches GAME_OVER, the server no longer sends role-filtered information, because hidden information is no longer meant to remain secret. Instead, the backend constructs a declassified endgame payload containing the winner, win reason, quest results, final score, and every player's revealed role and team. The React frontend then renders this payload through the result screen, showing the victory title, explanation, score summary, and declassified player list. The post-game reveal is itself part of the Avalon experience — players want to know who lied, who was Merlin, who sabotaged which quest, and most importantly whether their suspicions were correct.

The feature supports all of Avalon's ending branches. If Good completes three successful quests, the game enters the assassination phase rather than ending immediately. From there, the summary changes based on the Assassin's final decision: a correct guess flips the outcome to an Evil victory; an incorrect guess confirms Good's victory. If Evil instead wins earlier by sabotaging three quests, the game skips the assassination branch and the summary directly declares an Evil victory by quest failure. And if five consecutive teams are rejected without any approved vote, the engine ends the match early with an Evil victory and the summary displays this stall-out as the win reason (see Sub-Feature 2.4).

A match can also end without a decisive result: if a player disconnects and fails to return within the grace period (see Feature 6), the engine closes the match as abandoned. This still produces a Match record, but is excluded from player statistics (see Feature 9), since an abandoned game has no legitimate winner.

The endgame summary also connects the live match to persistent records. Once the game reaches GAME_OVER, the backend saves a Match document to MongoDB containing the room code, winner, win reason, quest history, and final player data. For signed-in users, the server also updates their long-term statistics, such as matches played and side-specific wins. This means the endgame summary is not only a visual closing screen for the current lobby, but also the bridge between a temporary live match and future match history or analytics features.

Trade-Offs: The endgame flow writes every match to MongoDB, including guest matches that may never be reviewed. This adds database dependency to the terminal state and creates persistent records for short-lived guest sessions. We accepted this because the Match document is also the foundation for Match History (Feature 8) and User Profile (Feature 9) — without saving every match, those features have no data to draw from.

Feature 6: Reconnection System (Final)

Sequence Diagram: Reconnection Grace Period and Socket ID Remapping

This sequence diagram shows why reconnection is handled as a server-side recovery flow rather than a normal join. When a player disconnects, the server temporarily preserves their seat, role, and active game state. If the player returns within the grace period, their new Socket.IO connection is mapped back to the existing player record. If the timer expires, the match is ended as abandoned and excluded from player statistics.

As a player who accidentally disconnects mid-match — through a tab refresh, network drop, or accidental browser close — I can rejoin the same game and instantly sync back to the current state, rather than losing progress for the entire lobby.

When a socket disconnects, the server does not immediately remove the player. Instead, disconnectHandlers.js starts a grace-period timer whose duration depends on what the player was actually doing at the moment of the drop. If an active, non-GAME_OVER game is running in that room, the player gets a 45-second window to return; if they were only sitting in the lobby, the window is 3 seconds. The distinction matters because the cost of waiting is asymmetric — holding a lobby slot open for a player who has closed the tab is pure friction for everyone else, whereas evicting someone mid-match destroys the game for all remaining players. During the grace period, the player's seat, role, and game state are preserved in memory, so a reconnecting socket is re-attached to the existing player rather than treated as a new joiner.

So, we realised a key edge case to be considered in our testing which is that reconnecting is not simply a new join. Socket.IO gives the returning player a new socket ID, so the server must remap the old ID to the new ID across role assignments, proposed teams, vote records, Evil chat rooms, and host status. Without this remapping, the same player could appear twice, lose their role, or have a previously cast vote counted under the wrong identity.

If the window lapses without a reconnection, the match can no longer continue with a missing player, and the engine ends it as an abandoned match — a distinct outcome from a decisive win, handled at GAME_OVER (see Feature 5) and deliberately excluded from player statistics (see Feature 9).

Trade-Offs: We originally planned to use Redis as an external store for active game state, which would have allowed a match to survive a server restart entirely. We delivered reconnection without it: an in-memory approach with a cleanup sweep was sufficient to handle the case that actually matters to players — an individual client dropping and returning — at our current single-instance scale. The cost is that this state lives inside the server process itself, so a server restart during an active match still loses the game, and the backend cannot be scaled across multiple instances without shared state coordination (see Known Limitations). A second trade-off is in test infrastructure: waiting 45 real seconds per disconnect scenario would make the integration suite impractically slow, so both windows collapse to 1500ms in test mode. This means our tests verify the logic of grace-period expiry and reconnection, not the exact production timings, which we accepted as a reasonable exchange for a test suite fast enough to run on every pull request.

Feature 7: Interactive Beginner Tutorial (Final)

Home Tutorial Overlay:

 first-time users are introduced to joining or hosting a session through a spotlight card

Lobby Tutorial Overlay

users are guided through the lobby before readying up, with the highlighted area showing the current context.

Quick Guide Modal

a separate rules reference for players who need to review mission flow, roles, voting, sabotage, and win conditions.

As a new user, I want a guided walkthrough of the interface so that I can navigate my first match comfortably without needing someone to explain the app to me.

The tutorial is a spotlight-style onboarding overlay implemented in BeginnerTutorial.tsx and wired into all three main pages — Home, Lobby, and Game. Each page defines its own step sequence in tutorialSteps.ts (5 steps for Home, 5 for Lobby, 6 for Game), and the overlay renders one step at a time: a dark backdrop, a glowing highlight ring around a specific interface element, and a card explaining what that element does, with Back, Skip, and Next controls.

Rather than screenshots or a mock interface, the tutorial highlights the real UI. Each step carries a targetId (such as alias-input, lobby-roster, or action-panel), and the corresponding components in the live page markup carry matching data-tutorial attributes. At render time the overlay locates the actual DOM node and draws the highlight around its real bounding box. This means the tutorial cannot drift out of sync with the interface it describes — if a panel moves or is restyled, the highlight follows it automatically.

When the tutorial runs it is deliberately different per page. On Home it auto-starts on first visit; on Lobby it auto-starts once the player's display name resolves; on Game it is manual-only, triggered by a "UI Guide" button. The Game page is the exception on purpose: auto-triggering an overlay during a live match would interrupt a player mid-decision, in a game where timing and attention are part of the play. Completion is tracked per-page in localStorage, so each walkthrough auto-runs only once per browser.

The tutorial is distinct from the "How to Play" guide (CipherGuideModal), which is a static reference for Avalon's roles and win conditions. The tutorial and quick guide serve different onboarding needs, where the tutorial explains how to use Cipher.gg's interface while the quick guide explains the underlying social deduction rules. Keeping them separate means a player who already knows Avalon isn't forced through rules they know, and a player who knows the rules but not our UI isn't left to guess.

Trade-Offs: Because the highlight targets live DOM nodes by data-tutorial attribute, a component removed or renamed without updating its attribute would leave a step pointing at nothing — a coupling between the tutorial and the markup that a screenshot-based walkthrough wouldn't have, but one we accepted in exchange for a tutorial that never shows a stale interface. A previously identified cosmetic gap was that exiting the tutorial via Skip or Finish caused an abrupt hard cut. We addressed this by wrapping the tutorial overlay in Framer Motion's AnimatePresence and adding an exit fade, so the onboarding layer now leaves the screen consistently with the rest of the animated UI.

Feature 8: Match History & Analytics Log (Final)

Match History Data Model

Match embeds quest history and vote attempts, while signed-in players are referenced through User IDs.

As a player, I want to review my completed matches so that I can look back at how a game actually unfolded, not just whether I won or lost.

Feature 8 is the read layer over the persistent Match records created at GAME_OVER. When a match ends, saveMatchRecord() formats every player with their userId or guestName, role, and team, then saves a Match document containing the room code, winner, win reason, quest history, and participating players. This means the live in-memory game state is converted into a permanent post-game record that can later be reviewed from the profile page.

The Match schema is intentionally match-centric. Each Match document embeds questHistory[], and each quest record can contain teamVoteHistory[]. This allows the system to preserve the full flow of a match: which quest was being attempted, who the leader was, which team was proposed, how players voted, whether the proposal was approved or rejected, and whether the quest was ultimately secured or compromised. This is important because in a social deduction game, rejected proposals and voting patterns are strategically meaningful; the final score alone does not explain how the table reached that result.

A signed-in player’s match history is retrieved by querying Match.find({ "players.userId": user._id }). The backend then formats each match into a profile-friendly summary containing the room code, winner, win reason, the player’s own role and team, whether they won, and the quest score. The frontend displays this through the Match History tab inside the Profile page, where each recent match shows the result, role, team, score, and win reason.

We chose to embed quest and vote history inside the Match document because this data is naturally owned by one match and is usually read together. When a player reviews a past game, the frontend needs the full timeline of that match rather than isolated vote records across all games. A more normalized schema could split Match, QuestRecord, and TeamVoteAttempt into separate collections, but that would make a simple match review require multiple joins or follow-up queries. Since Avalon has a bounded structure of five quests and at most five rejected team proposals before Evil wins, embedding the timeline keeps each Match document manageable while making post-game review straightforward.

Signed-in and guest players are handled differently. A signed-in player is stored inside players[] with a userId reference to their User document, which allows their matches to be queried later and linked to their profile. Guest players are still preserved in the Match document through guestName, role, and team, so the match record remains complete, but they cannot browse a personal history page because there is no persistent User identity to query across sessions.

Trade-Offs: The main trade-off is that the Match document can become heavier because it stores nested quests and voting history. However, this is acceptable for Cipher.gg because the game length is bounded by the Avalon rules, and the main use case is match-by-match review. In return, the system gains a trustworthy audit log that lets players analyze not only the outcome, but also the decisions, proposals, votes, and quest results that led to it.

Feature 9: User Profile (Final)

User Profile Overview

signed-in players can view their identity and cumulative performance statistics.

Recent Matches Tab

players can review their latest games, roles, results, and quest scores from their profile.

Sequence Diagram: From Game Over to Profile Statistics

As a returning player, I want a profile page showing my cumulative performance so that I can see how I'm doing across all my matches, not just the last one.

The profile page reads a signed-in player's User document, which carries both their identity (username, linked to their Clerk ID) and a stats object accumulating matchesPlayed, winsAsGood, winsAsEvil, and successfulAssassinations. Win rate and assassination accuracy are derived from these stored counters rather than recomputed by scanning match history, so displaying a profile is a single document lookup regardless of how many games the player has played.

These counters are updated once per match, immediately after GAME_OVER, via a bulk $inc operation in updateUserStatsAfterMatch(). Abandoned matches are explicitly excluded: a game that ended because someone failed to reconnect (see Feature 6) never touches anyone's statistics. This matters because an abandoned match has no legitimate winner — counting it either way would let a player inflate their win rate by disconnecting from a losing game, or unfairly penalise players for someone else's connection dropping.

Trade-Offs: Our schema has only one real relationship — a Match referencing the Users who played in it. Everything else, like quest history and votes, is naturally owned by a single match and is embedded directly rather than normalized across tables. A relational database would enforce that Match-to-User reference at the database level through a foreign key; MongoDB does not, so if a User document were ever deleted, old Match records could be left pointing to a user that no longer exists, with nothing to catch it. We accepted this because we prioritized iteration speed: as a two-person team, we continued refining core game rules throughout development, including changes made in this final milestone, such as widening the match-outcome options to account for abandoned games. MongoDB lets us make that kind of change without coordinating a schema migration across both of our environments. This risk is also low in our current production version, since we haven't implemented account deletion — the one scenario that would actually break this, a User being removed while old matches still reference them, cannot currently happen. It's something we'd need to revisit if that feature is ever added. We recognize a relational database would have worked equally well for a project of this size — this reflects a velocity trade-off that continued to pay off as our game rules kept evolving, right through to this final milestone.

Software Engineering

For Cipher.gg, a complex, real-time multiplayer engine, we recognized early on that without strict engineering and collaboration systems, our codebase would quickly become unmaintainable. Thus, we have adopted several Software Engineering (SE) practices to manage our development lifecycle.

1. Strict Version Control & Feature Branching 

We used Git as our version control system to track code history and manage branches, and GitHub as the collaboration platform to host our repository, run peer reviews through Pull Requests, and automate our CI/CD pipeline. Instead of pushing code directly to the main branch, we adopted a strict feature-branching workflow. This is because main is directly tied to production. Any merge triggers an automatic deployment to Vercel and Railway, so blocking direct pushes ensures every change is contained on its own branch until it's ready, rather than reaching production half-finished or untested. Every new component or mechanic, such as feature/game-over-ui or feature/assassination-ui, was developed on its own branch in isolation, allowing frontend and backend work to proceed in parallel without one blocking the other.

2. Peer Code Review & Pull Request Standards 

We also ensured no code was merged into the main repository without a formal Pull Request and peer review even though our frontend and backend are developed independently and rarely touch the same files. This is because review isn't only a conflict-resolution tool. A commit pushed straight to main is only visible after it's already deployed. A Pull Request can surface the change while it's still contained on a branch, giving us and CI pipeline the chance to catch a mistake and a failing test, before either ever reaches production. This practice was a game changer in maintaining code quality and catching critical errors early. Catching this in the PR review phase prevented a runtime crash on the frontend, proving the value of mandatory code review beyond just avoiding merge conflicts.

3. Project Management and Sprint Cadence

We managed development through feature branches and pull requests, with each major feature split into smaller implementation tasks. Our cadence followed the Orbital milestones:

  • MS1: core lobby, room joining, and fixed-size prototype gameplay.
  • MS2: full 5–10 player game engine, dynamic quest rules, role privacy, chat, and endgame summary.
  • MS3: reconnection, tutorial onboarding, match history, profile analytics, and documentation/testing polish.

For each feature, we tracked implementation tasks, review comments, and bug fixes through GitHub issues and pull requests. Pull requests were used not only to merge code but also to document design decisions and catch regressions through CI. When reviewer feedback surfaced gaps, such as role privacy clarity, reconnection edge cases, tutorial usability, or match-history persistence, these were converted into follow-up tasks rather than silently patched. This workflow helped us avoid treating the project as one large unstable branch. It also made review feedback actionable: instead of adding features randomly, we could turn each issue into a scoped branch, such as reconnection testing, beginner tutorial polish, server-side chat validation, or match-history persistence fixes.

4. Modular Design 

Another guiding SE principle for our project is the strict decoupling of our frontend client (React) and backend server (Node.js). For example, by isolating the RoleAssigner and AssassinationManager into self-contained modules, the backend acts purely as an authoritative finite state machine, while the frontend functions only as a presentation layer responsible only for rendering the UI and capturing player interactions. Because of this decoupling, we had to establish strict JSON data contracts for our WebSocket events and agree on the shape of the data payloads before writing the code, and this approach helped reduce integration bugs as it allowed us to work in parallel.

5. Continuous Integration (CI/CD) as a Gatekeeper 

To enforce our engineering standards automatically, we adopted a CI/CD pipeline using GitHub Actions to act as an automated gatekeeper. The full pipeline configuration and stages are documented in the CI/CD section below.

Quality Control

Testing Automation

In a real-time state orchestration engine managing complex rulesets like Avalon, manual testing of every possible edge case such as role distributions, dynamic quest team sizes, vote rejection limits, and the exact trigger conditions for the Assassination phase is both tedious and highly susceptible to human error. Thus, automated testing is essential because it provides a safety net as we scale the engine from the 5-player prototype into a 5 to 10 players game system. We rely on both unit and integration testing because they catch different classes of bugs: unit tests isolate a single function or class so failures point to exactly which piece of logic broke, while integration tests exercise real Socket.IO connections and MongoDB queries end-to-end, catching issues that only surface once modules are wired together. The following sections document our CI/CD pipeline, unit test coverage, integration test coverage, and a structured testing-case table maintained as a separate document.

Risk-Based Testing Strategy

Because Cipher.gg is a real-time hidden-role game, we did not treat all features as equal testing targets. UI-only features such as button styling or layout are lower risk, while backend state transitions, role privacy, reconnection, and persistence are high risk because a bug there can corrupt the match or leak hidden information. We therefore prioritized automated tests around:

1. Role invariants, such as tests that focus on teams with exactly one Merlin and one Assassin, correct Good/Evil ratios, and invalid player counts.

2. FSM permission checks, which includes invalid actions such as non-leader team proposals, duplicate votes, or out-of-phase events.

3. Boundary rules: 5-player minimum, 10-player maximum, Quest 4 two-fail rule, and five rejected teams.

4. Concurrency and timing, testing simultaneous vote submissions and disconnection/reconnection grace periods.

5. Persistence correctness: Match records, abandoned match handling, quest history, and user statistics updates.

This strategy reflects the risk profile of our system. A visual bug may reduce usability, but a backend FSM bug can change the winner, leak a hidden role, or corrupt a saved match. Therefore, our automated testing effort focuses most heavily on the backend game engine, Socket.IO integration, and MongoDB persistence. Frontend behaviours such as chat search, tutorial display, and visual rendering are currently covered through manual testing, ESLint, and Vite build checks. Component or end-to-end frontend tests are listed as a future improvement.

CI / CD

A robust Continuous Integration and Continuous Deployment (CI/CD) pipeline is strictly required in our project to protect the integrity of our repository as we collaborate as relying on local, simple test automation is insufficient because it depends on developers remembering to execute the scripts before committing. By utilizing GitHub Actions, our CI/CD pipeline acts as an automated gatekeeper and is configured to trigger automatically on pushes and Pull Requests to the main branch.

The stages included in our workflow (test.yml) are:

  1. Check out the repository and provision an isolated Node.js environment.
  2. Cleanly install all required packages to ensure consistency.
  3. Execute the complete Jest test suite and generate coverage reports for the backend, and also with strict ESLint and Vite build checks for the frontend.

These stages are critical as it enforces a mandatory quality standard before any code can be merged and completely eliminates discrepancies and ensures that only stable code is continuously deployed to our production servers on Vercel and Railway.

On the deployment side, merged code to main triggers automatic deployments through our hosting providers — Vercel watches the client/ directory and re-deploys the React frontend on every push, while Railway does the same for the server/ directory. This means a successful PR merge moves changes through testing into production with no manual deployment step, keeping our deployed prototype always in sync with the main branch.

Unit Testing

Unit testing involves isolating specific components, functions, or classes of the software and testing them independently to verify they perform exactly as intended. Our Jest unit tests cover role assignment, voting rules, quest logic, assassination logic, and win-condition evaluation. For a game engine based on The Resistance: Avalon, unit testing is critical because it verifies the underlying rules before they are exposed to network latency, Socket.IO events, or database persistence.

Unit Testing Coverage: The Game Engine

By testing both valid and invalid data boundaries, we ensured that the engine behaves predictably as the game scales beyond the original 5-player prototype. Specifically, we tested core state mutations to verify role distribution, team proposal validation, voting outcomes, quest resolution, and win-condition calculation.

For Milestone 2, our backend engine was upgraded from a fixed 5-player configuration to dynamic lobby support for 5 to 10 players. Therefore, our unit tests now validate the supported player-count range by checking the minimum valid boundary of 5 players, the maximum valid boundary of 10 players, and invalid out-of-range cases such as 4 and 11 players. This confirms that the engine accepts all valid Avalon lobby sizes while still rejecting unsupported configurations before they can enter the game loop.

We also tested that the RoleAssigner produces the correct Good/Evil ratio for each supported lobby size and always includes exactly one Merlin and one Assassin. For quest logic, we validated that the QuestManager applies the correct team sizes for 5, 6, 7, 8, 9, and 10-player games. This is important because Avalon does not use the same quest team size across all lobby sizes, so hardcoding the original 5-player rule would cause larger games to behave incorrectly.

In addition, we tested edge cases around the Quest 4 “two-fail required” rule. For 5 and 6-player games, Quest 4 only requires one fail vote to be compromised. For 7 to 10-player games, Quest 4 requires two fail votes. Our tests verify both sides of this boundary by confirming that a 7-player Quest 4 succeeds with only one fail, but fails once two fail votes are submitted.

We also considered abnormal action cases and player permissions, such as verifying that a non-leader cannot propose a team and that invalid assassination attempts are rejected. These tests prove that the game engine does not only handle happy-path gameplay, but also protects the game from illegal actions and boundary-case regressions as the ruleset expands.

Integration Testing

Integration testing verifies that different modules or services in the application work correctly when combined. Our suite includes integration tests spanning full Socket.IO game loops at 5, 7, and 10 player lobby sizes, plus dedicated tests for MongoDB persistence and user statistics updates. Integration testing is also important as it ensures data flows seamlessly across the network boundary, which in our case is between the React client and Node.js server.

Integration Testing Feature: The Socket.IO Pipeline

We tested the interaction between Socket.IO clients, the Node.js socket handlers, the backend game engine, and MongoDB persistence. This testing layer is crucial because a unit test can prove that an individual module works in isolation, but it cannot prove that real clients can successfully move through an entire match over WebSocket events.

Our integration tests simulate real player sockets joining a private room, readying up, starting the game, receiving role assignments, proposing teams, submitting team votes, resolving quests, and reaching game over. For Milestone 2, this was expanded beyond the original 5-player flow to include dynamic lobby sizes such as 5, 7, and 10 players. This gives us confidence that the full Socket.IO pipeline still works across the supported Avalon player range rather than only the original prototype configuration.

We also verified that the server persists completed matches correctly after game over. After a full game loop, the tests query MongoDB to confirm that a Match record was saved with the correct room code, winner, quest history, player roles, and team data. For signed-in test users, the integration tests also confirm that User statistics such as matchesPlayed, winsAsEvil, and winsAsGood are correctly updated after each match concludes. This ensures that the live real-time game flow is correctly connected to long-term persistence.

Testing Table Structure

The full testing table is maintained as a separate Excel document to keep the README readable. Instead of grouping tests only by generic categories such as "edge cases" or "unit tests", we reorganized the table by README feature. This makes it easier to evaluate whether each major feature has meaningful test coverage. Each feature is then broken down by scenario type:

  • Normal: expected user flow or successful gameplay path.
  • Abnormal: invalid user action or illegal game event.
  • Boundary: minimum/maximum supported values, such as 5-player and 10-player games.
  • Edge: uncommon but possible cases, such as five rejected teams.
  • Concurrency / Timing: real-time race-sensitive cases, such as reconnecting or voting around the same time.
  • Security / Privacy: hidden-role and data-masking cases where information leakage would break the game.
  • Persistence: database and long-term record correctness, such as match history and profile statistics.

We chose this structure because Cipher.gg's risk is not evenly distributed across all features. A UI display bug may affect usability, but a backend FSM, reconnection, role privacy, or persistence bug can corrupt the match result or leak hidden information. Grouping the tests by feature and scenario type helps us show not only how many tests exist, but which risks they are intended to cover. This also makes coverage gaps explicit since if a feature only has normal-path cases but no abnormal, boundary, edge, security, or persistence cases, it becomes immediately visible in the table.

Known Limitations & Looking Ahead

Although Cipher.gg now supports a complete real-time Avalon game loop for 5 to 10 players, including reconnection, onboarding, and post-game history, several limitations remain outside the current milestone's scope.

The first limitation is that active lobby and game state are held entirely in server memory. We originally planned to use Redis as a shared external store for this state, but ultimately delivered the Reconnection System without it. An in-memory approach with a cleanup sweep proved sufficient to let disconnected players rejoin and resync. The trade-off is that this state lives inside the server process itself, so a server restart during an active match would still lose the game, and the backend cannot be scaled across multiple instances without shared state coordination. Introducing Redis remains the natural next step if either becomes a real constraint.

The second limitation is frontend test automation. Our backend game engine and Socket.IO integration are covered by Jest unit and integration tests, and the frontend is checked through ESLint and Vite production builds. However, browser-level behaviours such as tutorial positioning, modal animations, chatbox search, private notepad editing, and multi-client dashboard rendering are still mainly verified through manual tests. A future Playwright or Cypress suite would let us test these flows across multiple simulated browser sessions.

Finally, three of our originally planned extension features were not implemented, as we prioritized completing the core game loop and its supporting systems within the remaining time:

  • Real-Time Voice Chat — voice communication during a round, as an alternative to typing.
  • Spectator Mode — allowing outside observers to watch a live game through a filtered data stream that hides secret role information.
  • Achievements — unlockable badges for milestones such as win streaks, tracked across multiple games.

Conclusion

Milestone 3 marked the transition from a functional Avalon platform to a complete, more complete and production-like platform. Where Milestone 2 focused on expanding the game engine to support dynamic lobbies and full rule coverage, this milestone focused on everything surrounding the match itself: surviving failure, welcoming new players, and giving results a life beyond the moment the game ends.

We delivered four features this milestone. The Reconnection System detects dropped connections and preserves a player's seat, role, and game state through a grace period calibrated to what they were doing at the time — 45 seconds mid-match, 3 seconds in the lobby — so a network drop no longer destroys the game for everyone else. The Interactive Beginner Tutorial guides new users through the real interface with a spotlight overlay anchored to live DOM elements, directly addressing the onboarding friction raised in peer review. Match History and User Profile complete the persistence story: every completed match is now browsable, and cumulative statistics let a player track their performance across games rather than just the last one.

The most valuable engineering lessons of this milestone came from the failure paths rather than the happy ones. Building reconnection forced us to confront timing behaviour we had previously been able to ignore — that a database lookup is a real network round trip, not an instant operation, and that a disconnect timer racing an in-flight reconnect is a genuine class of bug that only surfaces when tests run against real infrastructure rather than mocks. It also forced us to define what an abandoned match actually is: not a win, not a loss, and therefore something that must be recorded but deliberately excluded from a player's statistics. That single decision reached backwards into the endgame flow, the match schema, and the stats pipeline — a reminder that in a system with an authoritative server, a new edge case is rarely contained to one module.

We also made deliberate scope decisions rather than reaching for feature count. Real-Time Voice Chat, Spectator Mode, and Achievements were all cut, and Redis was deferred in favour of an in-memory approach that delivered reconnection at our current scale. We have documented each of these honestly in Known Limitations, along with what they would cost to revisit, because a clear account of what we chose not to build — and why — is a more useful engineering artefact than a longer list of half-finished features.

Cipher.gg now runs a complete, secure, real-time Avalon match from lobby to declassification, with an authoritative server that no client can deceive, an interface that teaches itself to newcomers, and a persistent record of every game played. It does what we set out to build: it removes the moderator from the table without removing anything that makes the game worth playing.
